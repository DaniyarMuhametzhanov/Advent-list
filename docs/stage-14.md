# Этап 14. Публикация

## 🔹 Что делаем и зачем

Сейчас календарь работает только на твоём компьютере: `http://localhost:8088`. Друзья его открыть не могут.

На этом этапе выкладываем календарь в интернет:

1. **Арендуем сервер** — компьютер в дата-центре, который работает круглые сутки.
2. **Привязываем домен** — адрес вроде `my-wishlist.ru`, по которому сайт найдут люди.
3. **Ставим Caddy** — программу, которая встречает посетителей и сама включает HTTPS (замочек в браузере).
4. **Прячем пароли** в файл `.env`, который живёт только на сервере.
5. **Настраиваем резервные копии** базы и картинок каждую ночь.
6. **Учимся читать логи** — журнал того, что происходит на сервере.

Аналогия 🏠: до сих пор ты собирал мебель у себя в мастерской (этап 13 — сложил всё в коробки). Теперь снимаем помещение (сервер), вешаем вывеску с адресом (домен), ставим на входе охранника с проверкой документов (Caddy и HTTPS), кладём ключи в сейф (`.env`) и раз в сутки делаем копию всех бумаг (бэкап).

Java-код и код фронтенда на этом этапе **не меняются**. Новые только файлы настроек и два маленьких скрипта.

⚠️ На этом этапе нужны **деньги и твои аккаунты**: аренда сервера и домена. Всё, что связано с покупкой и настройкой у провайдера, делаешь ты сам. В инструкции сказано, где нажимать и что выбирать.

## 🔹 Новые слова

| Термин | Простыми словами |
|---|---|
| **VPS** (virtual private server, виртуальный сервер) | «кусочек» большого компьютера в дата-центре, который сдают в аренду. Для тебя он выглядит как отдельный компьютер с Linux |
| **SSH** | способ управлять сервером через командную строку из своего компьютера. Как удалённый PowerShell |
| **SSH-ключ** (SSH key) | пара файлов вместо пароля. **Закрытый ключ** (private key) лежит только у тебя, **открытый** (public key) кладёшь на сервер. Подобрать нельзя, в отличие от пароля |
| **Домен** (domain) | имя сайта: `my-wishlist.ru`. Покупается у **регистратора** (registrar) на год |
| **DNS** | «телефонная книга» интернета: по имени домена находит IP-адрес сервера |
| **A-запись** (A record) | строчка в DNS: «домен `my-wishlist.ru` → IP `203.0.113.10`» |
| **HTTPS** | зашифрованное соединение. Без него пароль при входе можно подсмотреть в общем Wi-Fi |
| **Сертификат** (TLS certificate) | «паспорт» сайта, который подтверждает: это действительно `my-wishlist.ru`. Бесплатно выдаёт **Let's Encrypt** |
| **Caddy** | веб-сервер, который сам получает и продлевает сертификат. Встаёт перед nginx |
| **Переменные окружения** (environment variables) | настройки, которые программа получает при запуске, а не из кода. У нас они записаны в файле `.env` |
| **Файрвол** (firewall) | «забор» вокруг сервера: пропускает только разрешённые порты |
| **Резервная копия** (backup, бэкап) | копия данных, из которой можно всё вернуть, если что-то сломалось |
| **cron** | «будильник» Linux: запускает команду по расписанию |
| **Логи** (logs) | журнал: что программа делала и какие были ошибки |
| **Deploy key** (ключ развёртывания) | SSH-ключ, который даёт серверу право только **читать** один репозиторий на GitHub |

## 🔹 Как всё будет устроено

```
Браузер друга ──▶ https://my-wishlist.ru
                     │  DNS: my-wishlist.ru → IP сервера
                     ▼
   ┌──────────────── Сервер (VPS, Ubuntu) ────────────────────┐
   │  Файрвол: открыты только 22 (SSH), 80, 443                │
   │                                                           │
   │  ┌────────────── Docker-сеть ──────────────────────────┐  │
   │  │ caddy  :80 :443   ← единственный, кто смотрит наружу │  │
   │  │   │  HTTPS-сертификат, http → https                  │  │
   │  │   ▼                                                  │  │
   │  │ frontend (nginx)   /  → файлы React,  /api → backend │  │
   │  │   ▼                                                  │  │
   │  │ backend (Spring Boot, профиль prod)                  │  │
   │  │   │         │          │                             │  │
   │  │ postgres  redis      minio    ← портов наружу нет    │  │
   │  └──────────────────────────────────────────────────────┘  │
   │  .env (пароли)   backups/ (копии каждую ночь)             │
   └───────────────────────────────────────────────────────────┘
```

По сравнению с этапом 13 добавился только **Caddy** перед nginx. Всё остальное — те же контейнеры.

💡 Почему не открыть nginx прямо в интернет? Можно, но тогда сертификаты придётся получать и продлевать вручную (раз в 3 месяца). Caddy делает это сам.

💡 Мы уже готовились к этому на этапах 12 и 13:
* `application-prod.properties` берёт пароли из переменных `DB_PASSWORD` и `STORAGE_SECRET_KEY`, а cookie отправляет только по HTTPS.
* `server.forward-headers-strategy=native` — бэкенд верит заголовкам `X-Forwarded-*` от прокси и понимает, что запрос пришёл по HTTPS.
* nginx передаёт `X-Forwarded-Proto` дальше (шаг 5 этапа 13).
* миграция `db/prod` удаляет тестовых Анну, Бориса и Вику.

## 🔹 Шаг 1. Отдельный docker-compose для сервера

Почему не взять обычный `docker-compose.yml`? В нём у PostgreSQL, Redis и MinIO есть `ports:` — «двери» наружу (5434, 6379, 9000). На твоём компьютере это удобно: IntelliJ подключается к базе. А на сервере это значит, что **любой человек в интернете** сможет постучаться в базу. Плюс там простые пароли `advent`.

Поэтому для сервера делаем **отдельный** файл. Создай в корне проекта `docker-compose.prod.yml`:

```yaml
# Всё приложение для настоящего сервера (этап 14).
# Запуск на сервере: docker compose -f docker-compose.prod.yml up -d --build
# Пароли и домен берутся из файла .env рядом с этим файлом (образец — .env.example)
name: advent

# Общие настройки логов: каждый файл до 10 МБ, хранить 3 файла. Иначе логи когда-нибудь займут весь диск
x-logging: &logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  # Единственная «дверь» в интернет. Принимает запросы на 80 и 443, сам получает
  # HTTPS-сертификат для домена и передаёт всё в frontend (nginx)
  caddy:
    image: caddy:2
    environment:
      DOMAIN: ${DOMAIN:?впиши DOMAIN в .env}
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"   # HTTP/3
    volumes:
      - ./deploy/Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data       # здесь лежат сертификаты. Потеряешь — Caddy просто получит новые
      - caddy-config:/config
    depends_on:
      - frontend
    restart: unless-stopped
    logging: *logging

  # nginx с фронтендом. Портов наружу нет: к нему ходит только Caddy
  frontend:
    build: ./frontend
    depends_on:
      - backend
    restart: unless-stopped
    logging: *logging

  backend:
    build: ./backend
    environment:
      SPRING_PROFILES_ACTIVE: prod
      DB_PASSWORD: ${DB_PASSWORD:?впиши DB_PASSWORD в .env}
      STORAGE_SECRET_KEY: ${STORAGE_SECRET_KEY:?впиши STORAGE_SECRET_KEY в .env}
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/advent
      SPRING_DATA_REDIS_HOST: redis
      STORAGE_ENDPOINT: http://minio:9000
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      minio:
        condition: service_started
    restart: unless-stopped
    logging: *logging

  # База, Redis и MinIO — без ports: из интернета до них не достучаться
  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: advent
      POSTGRES_USER: advent
      POSTGRES_PASSWORD: ${DB_PASSWORD:?впиши DB_PASSWORD в .env}
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U advent -d advent"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped
    logging: *logging

  redis:
    image: redis:8
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped
    logging: *logging

  minio:
    image: pgsty/minio:RELEASE.2026-08-04T00-00-00Z
    command: server /data
    environment:
      MINIO_ROOT_USER: advent
      MINIO_ROOT_PASSWORD: ${STORAGE_SECRET_KEY:?впиши STORAGE_SECRET_KEY в .env}
    volumes:
      - minio-data:/data
    restart: unless-stopped
    logging: *logging

volumes:
  postgres-data:
  minio-data:
  caddy-data:
  caddy-config:
```

Разбор по частям:

* `name: advent` — имя проекта для Docker. От него зависят имена томов: `advent_postgres-data`, `advent_minio-data`. Они понадобятся в скриптах бэкапа.
* `x-logging: &logging` — общий кусок настроек. `&logging` — дать ему имя (**якорь**, anchor), а `logging: *logging` в каждом сервисе — вставить его туда. Сами настройки ограничивают размер логов: иначе через полгода они займут весь диск.
* `${DB_PASSWORD:?впиши DB_PASSWORD в .env}` — взять значение из `.env`. Если его нет, Docker **откажется запускаться** и напишет этот текст. Это лучше, чем запуститься с пустым паролем.
* У `caddy` есть `ports` 80 и 443 — это **единственная** дверь наружу. 80 нужен, чтобы Let's Encrypt проверил домен и чтобы перенаправлять `http://` на `https://`. `443/udp` — для нового быстрого протокола HTTP/3.
* `caddy-data` — том, где Caddy хранит сертификаты. Без него после каждого перезапуска Caddy просил бы новый сертификат, а Let's Encrypt ограничивает число выдач.
* У `frontend`, `backend`, `postgres`, `redis`, `minio` **нет** `ports`. Они видят друг друга внутри Docker-сети, а снаружи их нет.
* `SPRING_PROFILES_ACTIVE: prod` — включить `application-prod.properties` (этап 12).
* `MINIO_ROOT_PASSWORD: ${STORAGE_SECRET_KEY...}` — MinIO и бэкенд берут **один и тот же** пароль из `.env`, поэтому они всегда совпадают.
* `restart: unless-stopped` — если сервер перезагрузится или программа упадёт, Docker поднимет её снова. Не поднимет, только если ты сам остановил её командой.
* У MinIO убрали `--console-address ":9001"`: веб-панель MinIO на сервере не нужна.

## 🔹 Шаг 2. Настройки Caddy

Создай папку `deploy` в корне проекта, а в ней файл `Caddyfile` (без расширения):

```
# Caddy: принимает запросы из интернета и передаёт их nginx (сервис frontend).
# {$DOMAIN} — домен из файла .env. Для него Caddy сам получит и будет продлевать HTTPS-сертификат
{$DOMAIN} {
	# Браузер запомнит: на этот сайт ходить только по HTTPS (HSTS). 31536000 секунд = год
	header Strict-Transport-Security "max-age=31536000"
	# Не писать в ответах, что сервер — Caddy
	header -Server

	reverse_proxy frontend:80

	# Журнал запросов (кто, когда, какой адрес). Смотреть: docker compose ... logs caddy
	log
}
```

Разбор:

* `{$DOMAIN}` — подставить домен из переменной `DOMAIN`. Увидев имя домена, Caddy **сам** получит для него сертификат у Let's Encrypt и будет продлевать его. Ничего больше для HTTPS писать не нужно.
* `Strict-Transport-Security` (**HSTS**) — браузер запомнит, что этот сайт открывается только по HTTPS, и не пойдёт на `http://` даже если человек так напишет.
* `header -Server` — убрать заголовок с названием сервера. Чем меньше чужой человек знает о сервере, тем лучше (как `server_tokens off` в nginx).
* `reverse_proxy frontend:80` — передать всё в nginx. Caddy сам добавит `X-Forwarded-For` (настоящий адрес посетителя) и `X-Forwarded-Proto: https`.
* `log` — записывать каждый запрос в журнал.

💡 Важно: в Caddyfile отступы делаются **табуляцией**, а не пробелами. Caddy простит и пробелы, но так принято.

## 🔹 Шаг 4. Скрипт резервной копии

Создай `deploy/backup.sh`:

```sh
#!/bin/sh
# Резервная копия: база данных и картинки. Кладёт файлы в папку backups/
# Запуск вручную: sh deploy/backup.sh   (cron запускает его сам каждую ночь)
set -eu
# Для Git Bash на Windows: не превращать пути вроде /data в C:/Program Files/Git/data
export MSYS_NO_PATHCONV=1

cd "$(dirname "$0")/.."          # перейти в папку проекта, откуда бы ни запустили
mkdir -p backups
STAMP=$(date +%Y-%m-%d_%H-%M)

# 1. База: pg_dump выгружает всё в SQL-текст, gzip сжимает
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U advent -d advent --clean --if-exists | gzip > "backups/db-$STAMP.sql.gz"

# 2. Картинки: упаковываем содержимое тома MinIO в архив
docker run --rm -v advent_minio-data:/data:ro alpine:3.22 \
  tar -C /data -czf - . > "backups/images-$STAMP.tar.gz"

# 3. Удаляем копии старше 14 дней, чтобы не забить диск
find backups -name '*.gz' -mtime +14 -delete

echo "Готово: backups/db-$STAMP.sql.gz и backups/images-$STAMP.tar.gz"
```

Разбор:

* `#!/bin/sh` — «выполнять этот файл программой `sh`» (командная оболочка Linux).
* `set -eu` — остановиться при первой ошибке (`-e`) и при опечатке в имени переменной (`-u`). Без этого скрипт мог бы «успешно» сделать пустую копию.
* `export MSYS_NO_PATHCONV=1` — нужно только для Git Bash на Windows (шаг 7): без этого он «помогает» и превращает `/data` в путь Windows. На сервере ничего не меняет.
* `cd "$(dirname "$0")/.."` — `$0` — путь к самому скрипту, `dirname` — его папка (`deploy`), `/..` — на уровень выше. Скрипт сам переходит в корень проекта, откуда бы его ни запустили (cron запускает из домашней папки).
* `pg_dump` — программа PostgreSQL, которая выгружает всю базу в текст из SQL-команд. `--clean --if-exists` — добавить в начало команды «удалить старые таблицы, если есть», чтобы при восстановлении не было конфликтов.
* `exec -T postgres ...` — выполнить команду **внутри** работающего контейнера. `-T` — без интерактивного терминала, нужно, когда вывод идёт в файл.
* `| gzip > файл` — сжать вывод и записать в файл. SQL-текст сжимается раз в 5–10.
* `docker run --rm -v advent_minio-data:/data:ro alpine:3.22 tar ...` — запустить крошечный временный контейнер Alpine Linux, подключить к нему том с картинками **только для чтения** (`:ro`) и упаковать всё в архив. `--rm` — удалить контейнер после работы.
* `find backups -name '*.gz' -mtime +14 -delete` — удалить копии старше 14 дней (`-mtime +14`).

## 🔹 Шаг 5. Скрипт восстановления

Бэкап, из которого ни разу не восстанавливались, — это не бэкап, а надежда 🙂. Поэтому сразу пишем и восстановление. Создай `deploy/restore.sh`:

```sh
#!/bin/sh
# Восстановление из резервной копии. ВНИМАНИЕ: текущие данные заменятся данными из копии.
# Запуск: sh deploy/restore.sh backups/db-ДАТА.sql.gz backups/images-ДАТА.tar.gz
# Картинки можно не указывать — тогда восстановится только база
set -eu
# Для Git Bash на Windows: не превращать пути вроде /data в C:/Program Files/Git/data
export MSYS_NO_PATHCONV=1

DB_FILE=$(realpath "$1")                  # полный путь к файлам, пока мы не сменили папку
IMG_FILE=${2:+$(realpath "$2")}
cd "$(dirname "$0")/.."
DC="docker compose -f docker-compose.prod.yml"

# 1. Останавливаем бэкенд, чтобы никто не менял данные во время восстановления
$DC stop backend

# 2. База: в копии сначала идут команды «удалить таблицу», потом «создать и заполнить»
gunzip -c "$DB_FILE" | $DC exec -T postgres psql -q -U advent -d advent -v ON_ERROR_STOP=1

# 3. Картинки: очищаем том MinIO и распаковываем туда архив
if [ -n "$IMG_FILE" ]; then
  $DC stop minio
  docker run --rm -i -v advent_minio-data:/data alpine:3.22 \
    sh -c 'rm -rf /data/* /data/.[!.]*; tar -C /data -xzf -' < "$IMG_FILE"
  $DC start minio
fi

# 4. Кэш в Redis хранит старые данные — очищаем его
$DC exec -T redis redis-cli FLUSHALL

$DC start backend
echo "Восстановлено из $DB_FILE"
```

Разбор:

* `realpath "$1"` — превратить путь вроде `backups/db-...` в полный (`/home/deploy/advent-list/backups/db-...`). Нужно сделать **до** `cd`, иначе относительный путь потеряется.
* `${2:+...}` — «если второй аргумент есть, то вот это, иначе пусто». Так картинки можно не указывать.
* `stop backend` — пока идёт восстановление, никто не должен менять данные.
* `gunzip -c | psql` — распаковать копию и выполнить все SQL-команды в базе. `ON_ERROR_STOP=1` — остановиться при первой ошибке.
* `rm -rf /data/* /data/.[!.]*` — удалить всё в томе MinIO, включая скрытые папки (MinIO хранит служебное в `.minio.sys`).
* `redis-cli FLUSHALL` — очистить кэш (этап 11). Иначе бэкенд какое-то время показывал бы данные «до восстановления».

⚠️ После восстановления **всем придётся войти заново**: сессии сбрасываются вместе с кэшем. Это нормально.

# Часть 2. Сервер

## 🔹 Шаг 9. Арендовать VPS

Это делаешь ты сам у любого хостинг-провайдера (ищи «VPS» или «облачный сервер»). Что выбрать:

| Параметр | Что брать | Почему |
|---|---|---|
| Операционная система | **Ubuntu 24.04** | самая популярная, по ней больше всего инструкций |
| Память (RAM) | **от 2 ГБ** | Java, PostgreSQL, MinIO, Redis и сборка Maven вместе. С 1 ГБ сборка упадёт |
| Процессор | 1–2 ядра | хватит |
| Диск | от 20 ГБ | система, Docker-образы, база, картинки, копии |
| Доступ | **по SSH-ключу** | см. шаг 10, ключ создай заранее |

Провайдер покажет **IP-адрес** сервера, например `203.0.113.10`. Запиши его. Дальше в инструкции вместо `203.0.113.10` подставляй свой.

## 🔹 Шаг 10. SSH-ключ

Пароль можно подобрать, ключ — нет. Поэтому заходим на сервер по ключу.

В PowerShell на своём компьютере:

```powershell
ssh-keygen -t ed25519 -C "daniyar-laptop"
```

* `-t ed25519` — тип ключа: современный, короткий и надёжный.
* `-C "..."` — подпись, чтобы потом понимать, чей это ключ.

На все вопросы можно нажать Enter (файл по умолчанию, пароль на ключ — по желанию). Появятся два файла в `C:\Users\rando\.ssh\`:

* `id_ed25519` — **закрытый** ключ. Никому не показывай и никуда не загружай.
* `id_ed25519.pub` — **открытый** ключ. Его можно давать кому угодно.

Покажи открытый ключ и скопируй его целиком:

```powershell
Get-Content $HOME\.ssh\id_ed25519.pub
```

При создании сервера у провайдера будет поле «SSH-ключ» — вставь туда эту строку. Если сервер уже создан с паролем, ключ добавим в шаге 12.

## 🔹 Шаг 11. Первый вход

```powershell
ssh root@203.0.113.10
```

При первом входе спросит `Are you sure you want to continue connecting?` — напиши `yes`. Это сервер показывает свой «отпечаток», и твой компьютер его запоминает.

Ты внутри сервера. Приглашение командной строки стало вроде `root@server:~#`. Все команды дальше в части 2 — **на сервере**, пока не сказано иначе.

Обнови систему:

```sh
apt update && apt upgrade -y
```

* `apt` — «магазин программ» Ubuntu. `update` — обновить список, `upgrade -y` — поставить обновления, на вопросы отвечать «да».

## 🔹 Шаг 12. Отдельный пользователь

`root` — пользователь с полными правами. Работать под ним постоянно опасно: одна опечатка в команде, и можно стереть систему. Создадим обычного пользователя `deploy`:

```sh
adduser deploy
usermod -aG sudo deploy
```

* `adduser deploy` — создать пользователя. Спросит пароль (придумай и запиши — он нужен для `sudo`), остальные вопросы можно пропустить Enter.
* `usermod -aG sudo deploy` — добавить его в группу `sudo`: он сможет выполнять команды администратора, написав перед ними `sudo`.

Скопируй ему свой SSH-ключ:

```sh
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy
```

(Если сервер создан с паролем, а не с ключом: на **своём** компьютере выполни
`Get-Content $HOME\.ssh\id_ed25519.pub | ssh deploy@203.0.113.10 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"`.)

**Не закрывая** текущее окно, открой второе окно PowerShell и проверь:

```powershell
ssh deploy@203.0.113.10
```

Пустило без пароля — отлично. Дальше работаем под `deploy`, окно с `root` можно закрыть.

## 🔹 Шаг 13. Файрвол

Разрешим только три порта: 22 (SSH), 80 и 443 (сайт). Всё остальное закрыто.

```sh
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443
sudo ufw enable
sudo ufw status
```

* `ufw` (uncomplicated firewall) — простая настройка файрвола в Ubuntu.
* `allow OpenSSH` — **сначала** разрешаем SSH. Если включить файрвол без этого, ты сам себя выкинешь с сервера.
* `allow 443` без `/tcp` — и TCP, и UDP (HTTP/3).

💡 Docker умеет обходить `ufw` для портов из `ports:`. Поэтому так важно, что у базы, Redis и MinIO в `docker-compose.prod.yml` **нет** `ports`: даже если файрвол настроен с ошибкой, до них не достучаться.

## 🔹 Шаг 14. Запретить вход по паролю

Теперь, когда вход по ключу работает, отключим вход по паролю. Боты круглосуточно перебирают пароли на всех серверах в интернете, а без пароля им перебирать нечего.

```sh
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```

`nano` — простой текстовый редактор в терминале. Впиши:

```
PasswordAuthentication no
PermitRootLogin no
```

Сохранить: `Ctrl+O`, Enter. Выйти: `Ctrl+X`. Применить:

```sh
sudo systemctl restart ssh
```

⚠️ **Не закрывай текущее окно.** Открой новое и проверь, что `ssh deploy@203.0.113.10` по-прежнему пускает. Если нет — в старом окне удали этот файл (`sudo rm /etc/ssh/sshd_config.d/99-hardening.conf`) и перезапусти ssh снова.

## 🔹 Шаг 15. Файл подкачки (swap)

Сборка бэкенда в Maven на короткое время просит много памяти. **Swap** (файл подкачки) — это кусок диска, который Linux использует как запасную память, когда обычная кончается. Медленно, но сборка не упадёт.

```sh
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h
```

* `fallocate -l 2G` — создать файл на 2 ГБ.
* `chmod 600` — читать его может только система.
* `mkswap` и `swapon` — разметить файл как swap и включить.
* строка в `/etc/fstab` — включать swap и после перезагрузки.
* `free -h` — в строке `Swap` должно быть `2.0Gi`.

## 🔹 Шаг 16. Установить Docker

Официальный способ от Docker:

```sh
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker deploy
```

* Первая команда скачивает установочный скрипт Docker и запускает его.
* Вторая — разрешает пользователю `deploy` управлять Docker без `sudo`.

Выйди (`exit`) и зайди снова (`ssh deploy@203.0.113.10`), чтобы новая группа заработала. Проверь:

```sh
docker run --rm hello-world
docker compose version
```

Должно напечатать `Hello from Docker!` и версию Compose.

## 🔹 Шаг 17. Купить домен и направить его на сервер

Домен покупаешь сам у любого регистратора доменов. Потом в его панели найди раздел **DNS** (или «Управление зоной», «DNS-записи») и добавь запись:

| Тип | Имя (хост) | Значение | TTL |
|---|---|---|---|

## 🔹 Шаг 18. Доступ сервера к GitHub

Репозиторий закрытый, поэтому серверу нужно право его читать. Дадим ему **deploy key** — ключ, который может только читать один этот репозиторий. Если сервер взломают, злоумышленник не получит доступ к твоему GitHub-аккаунту.

```
Host github.com
```

# Часть 5. Резервные копии

## 🔹 Шаг 23. Копия каждую ночь

Сначала сделай копию вручную и убедись, что работает:

```sh
cd ~/advent-list
sh deploy/backup.sh
ls -lh backups
```

Теперь попросим **cron** делать это каждую ночь:

```sh
crontab -e
```

При первом запуске спросит, каким редактором пользоваться — выбери `nano` (обычно пункт 1). В конец файла добавь строку:

```
30 3 * * * sh /home/deploy/advent-list/deploy/backup.sh >> /home/deploy/backup.log 2>&1
```

Разбор:

* `30 3 * * *` — расписание: минута `30`, час `3`, любой день месяца, любой месяц, любой день недели. То есть каждую ночь в 03:30 (по времени сервера, обычно это UTC).
* `sh .../backup.sh` — что запускать. Путь полный: cron не знает, в какой ты папке.
* `>> /home/deploy/backup.log 2>&1` — дописывать вывод и ошибки в журнал. Утром можно открыть `cat ~/backup.log` и увидеть, всё ли прошло.

## 🔹 Шаг 24. Копия не только на сервере

Если у провайдера сгорит диск, вместе с сервером пропадут и копии в `backups/`. Поэтому иногда (например, раз в неделю) забирай копии к себе. В PowerShell на **своём** компьютере:

```powershell
mkdir $HOME\advent-backups -Force
scp "deploy@203.0.113.10:advent-list/backups/*" $HOME\advent-backups\
```

`scp` — «копировать по SSH». Сначала откуда (`сервер:путь`), потом куда (папка на компьютере).

💡 Многие провайдеры VPS умеют делать **снимок** (snapshot) всего диска сервера по расписанию за небольшие деньги. Это хорошее дополнение, но не замена: со снимком ты вернёшь весь сервер целиком, а из своих копий — именно данные, на любой другой сервер.

## 🔹 Шаг 25. Как восстановить


# Часть 6. Логи

## 🔹 Шаг 26. Где смотреть, что происходит

Все команды — на сервере, в папке `~/advent-list`. Чтобы не писать каждый раз длинное `-f docker-compose.prod.yml`, сделай сокращение (**alias**):

```sh
echo "alias dc='docker compose -f ~/advent-list/docker-compose.prod.yml'" >> ~/.bashrc
source ~/.bashrc
```

Теперь `dc` — это `docker compose -f ~/advent-list/docker-compose.prod.yml`.

| Команда | Что показывает |
|---|---|
| `dc ps` | какие сервисы работают, какие упали |
| `dc logs backend --tail 100` | последние 100 строк журнала бэкенда |
| `dc logs -f backend` | журнал бэкенда «вживую» (выйти: `Ctrl+C`) |
| `dc logs backend --since 1h` | журнал за последний час |
| `dc logs backend \| grep -i error` | только строки с ошибками |
| `dc logs caddy --tail 50` | последние запросы к сайту: адрес, путь, код ответа |
| `docker stats` | сколько памяти и процессора берёт каждый контейнер (выйти: `Ctrl+C`) |
| `df -h /` | сколько места на диске свободно |

Как искать проблему:

1. Сайт не открывается совсем → `dc ps` (работает ли `caddy`?) и `dc logs caddy`.
2. Сайт открывается, но вход или данные не работают → `dc logs backend --tail 200`, ищи `ERROR` и `Exception`.
3. Медленно → `docker stats` и `free -h`: не кончилась ли память.

| `ssh: connect to host ... Connection timed out` | неверный IP или файрвол закрыл 22 | проверь IP; в веб-консоли провайдера выполни `sudo ufw allow OpenSSH` |
| `Permission denied (publickey)` | на сервере нет твоего открытого ключа | шаг 12, команда в скобках |
| `required variable DB_PASSWORD is missing` (или с текстом «впиши ... в .env») | нет `.env` или в нём пустое значение | шаг 20 |
| Сборка бэкенда падает с `Killed` или `exit code: 137` | кончилась память | шаг 15 (swap) или сервер с 2 ГБ+ |
| В логе Caddy `challenge failed` или `NXDOMAIN` | DNS ещё не указывает на сервер или порт 80 закрыт | `nslookup` (шаг 17), `sudo ufw status` (шаг 13). Подожди и перезапусти: `dc restart caddy` |
| В логе Caddy `too many failed authorizations` / `rateLimited` | слишком много неудачных попыток получить сертификат | исправь DNS и подожди час, Caddy попробует снова сам |
| Сайт отвечает `502 Bad Gateway` | бэкенд ещё запускается или упал | подожди минуту; потом `dc logs backend` |
| В логе бэкенда `password authentication failed for user "advent"` | пароль в `.env` поменяли после первого запуска | верни прежний пароль в `.env` |
| Вход работает, но сразу выкидывает обратно | cookie только для HTTPS, а сайт открыт по `http://` | открывай `https://`; проверь, что запросы идут через Caddy |
| Картинка не загружается, `413` | файл больше 5 МБ | это ограничение задумано (этап 8) |
| Закончилось место (`no space left on device`) | старые образы, логи, копии | `docker image prune -f`, `docker builder prune -f`, проверь `du -sh ~/advent-list/backups` |

## Главное, что нужно запомнить

* **Наружу смотрит только Caddy** (порты 80 и 443). База, Redis и MinIO живут без `ports` и из интернета недоступны.
* **Caddy сам получает и продлевает HTTPS-сертификат**, если DNS домена указывает на сервер и открыт порт 80.
* **Пароли — только в `.env` на сервере**, в Git лежит лишь образец `.env.example`. Копию `.env` храни в менеджере паролей.
* **Бэкап, который ни разу не восстанавливали, — не бэкап.** Копии каждую ночь по cron, иногда забирай их к себе.
* **Логи — первое место, куда смотреть**, когда что-то сломалось: `dc ps`, потом `dc logs <сервис>`.
